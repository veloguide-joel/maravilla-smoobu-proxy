## 0. Findings in brief
1. **The existing path already suffices for OBSERVATION; no new event or schema is needed to record what the owner did.** `booking.admin_record_evidence` (0003 §C4, superseded in 0010) writes an **owner-attested, dashboard-sourced, append-only `provider_evidence` row** bound to the intent and the provider object (PI / reservation / offline-charge list), with mandatory `attested_by` + `reference`, status vocabulary validation, `observed` JSON (ids / amounts / statuses only), recorded role + session user, admin-only EXECUTE. It changes **no** intent row, version, claim, op, ledger or transition row — **but it is not semantically inert**: `authorization_blockers` / `reservation_blockers` (0003:146-193; `authorization_blockers` replaced in 0019:289 with the same evidence selection) pick the latest `provider_evidence` row by `observed_at DESC, created_at DESC` **with no source filter**, so a dashboard INSERT can change their results (and, through them, `claim_release_blockers` in a releasable state and `admin_resolve_intent` decisions) while every intent/op/claim/ledger row stays byte-identical. Proven in C15 O1 (§7). Accepted tests cover the primitive (`test/db/e2b1-safety.test.mjs` "dashboard evidence: admin only, with attestation and reference"; `e7-test-abort.test.mjs` uses dashboard rows as conflicting evidence).
2. **`ESCALATE` is NOT an observation primitive.** `intent-state.js:321-322, :680-681`: it moves the intent to `reconciliation_required` (new version, `reasonCode`, `alert.owner` effect) and the only exits are `RESOLVE confirmed | released | cancelled` (`:777-792`; DB side `admin_resolve_intent` 0003:603, unchanged through 0021), each of which *changes state again*. For a captured payment, `released`/`cancelled` are blocked (they need `authorization_blockers` empty, i.e. PI `canceled`/`requires_payment_method`, and a captured PI reads `succeeded`); **`confirmed` IS reachable** with cited `hostaway_reservation found_active` evidence matching listing/from/to/total plus `payment_intent succeeded` evidence with `amountReceivedMinor` = total — it moves the intent to `confirmed` with no offline charge recorded. So ESCALATE is not a dead end, but it is still the wrong tool for observation: it changes state and version, sets `reasonCode`, queues `alert.owner`, and its only resolutions re-enter the booking state machine. **Do not use ESCALATE for observation.**
3. **`reconciliation_cases` / `reconciliation_resolutions` are not needed for observation either.** Cases are opened only by workers / DB fences (0011/0013/0015/0016 inserts; `mv_booking_app` has no UPDATE, there is no `admin_open_case`); `admin_close_case` requires an open case; `admin_resolve_intent` requires `reconciliation_required`. For a `payment_captured` intent with no open case there is nothing to resolve — and that is correct: a manual disposition does not resolve the booking state, it is a fact *about the providers*.
4. **What the DB cannot express today (gaps, all tolerable for observation):** a manual Stripe refund has **no ledger / `payment_refunds` row** (`payment_refunds` requires `requested_by ∈ {admin, system}` through the guarded request path, `refund_succeeded` is written only by the cleanup repo path, `repo.js:272`); a manual Hostaway cancel of a *captured* booking has no state (`payment_captured` admits no `RESERVATION_CANCELLED`); so after such a disposition **`intents` will keep saying `payment_captured` / `captured_minor` 14000 while `provider_evidence` says refunded / cancelled.** That is an *explicit, queryable discrepancy*, not a silent one, and it is acceptable until a reviewed action exists (§5). It must never be "fixed" by inference.

## 2. Admissible observation record — exact rules (reuse of `admin_record_evidence`; nothing new)
**Actor.** The owner (Joel) attests what he saw / did in the provider dashboards; the row is written by a reviewed admin session (`mv_booking_admin` or the schema owner — ROOT's SQL-editor session qualifies), `attested_by` = owner label, `reference` = where it can be re-checked (dashboard URL + Stripe request id / event id, Hostaway log line time). Claude never writes. The write is **DB persistence** (an INSERT); it is "read-only" only with respect to providers, money and booking state — say so explicitly in any packet.
**Freshness (packet policy — NOT DB-enforced).** `observed_at` = the actual dashboard read time; the ≤ 10-min rule and the "newer than the last state-changing run" rule are reviewer policy: the DB only enforces shape/status/attestation and then **consumes whatever row has the newest `observed_at`** (C15 O2). "Never back-dated" means **never invent a timestamp**; an actual historical `observed_at` may be inserted later, but **only under a separately reviewed insertion whose full predicate impact has been assessed first**, because: a historical row whose `observed_at` is newer than everything stored becomes the current reading; a historical row older than the stored newest is not consumed as current but is still appended and visible; a `reference` saying "history" has **no** effect on consumption (there is no inert/history-only mode). Equal `observed_at` → the later-created row wins.
**Binding (must all hold, checked by the reviewer before the INSERT; the DB checks kind/status/shape only).**
- `intent_id` = the DB intent; `external_ref` = **exactly** `intents.stripe_payment_intent_id` (PI) or `intents.hostaway_reservation_id` (R) — never an id from a different attempt / session; for an offline-charge list, `external_ref` = R and the list is the Hostaway charges page for R.
- Money: `observed.amountMinor` = `intents.final_total_minor`; `observed.currency` = `intents.currency` (USD, upper case); amounts in **minor units** (USD 140.00 = 14000); `amountReceivedMinor`, `amountCapturableMinor`, `amountRefundedMinor`, `chargeId`, `captured`, `refunded` recorded as observed (free JSON keys are allowed by `validate_evidence`; `amountReceivedMinor` is the key the existing resolve predicate reads).
- Identity: for `hostaway_reservation` status `found_active`, `listingId`/`from`/`to`/`totalMinor` must equal the intent's; `bookingRef` = `intents.ref` when visible (field 105433).
- Provenance: `reference` must name the exact artefact (e.g. `stripe:req_tIG0i81IDWcZAU` for `pi_3UbR9W…`'s capture; `hostaway:reservation 71692858 logs 2026-11-13 17:56:05Z` for the host cancellation of **R71692858** — R71700931 has no cancellation and an empty log).
- **Mandatory vs optional.** Identity and payment proof fields (intent ↔ PI/R binding, `status` as displayed, amount + currency for found_active / succeeded) are **mandatory: missing → STOP, no INSERT**. Raw fields the dashboard does not expose (e.g. charge `captured`/`refunded` when not rendered — C12 precedent) are **optional: left absent and reported UNKNOWN, never inferred**; `validate_evidence` enforces only the shape listed in §1, not these policy rules.
**Owner-reported vs provider-verified.** A dashboard row (`*_dashboard`, attested) is *owner-reported*; a `*_api` row bound to a succeeded read op is *provider-verified*. Both are admissible observations and **both feed the existing predicates equally** (no source filter — F1); the distinction is provenance for the reviewer, not a DB privilege. API rows arrive only through a reviewed read dispatch (the hosted runners' PI/reservation reads persist evidence in their own flows). Nothing in this review asks for such a dispatch.

## 4. STOP rules for observation (the reviewer applies them; the DB cannot)
- **Stale**: `observed_at` older than 10 min at INSERT, or older than the latest `intent_transitions.at` for that intent → STOP (record only as dated history with `reference` saying so, or not at all).
- **Missing**: any binding field in §2 absent (PI id ≠ intent's, R ≠ intent's, amount/currency missing or in major units) → STOP; `validate_evidence` will also refuse malformed shapes but it does not know the intent's amounts.
- **Conflicting**: an observation that contradicts an existing `*_api` evidence row newer than it, or two owner rows that disagree → STOP; record nothing new until re-read; never pick one by preference.
- **Unknown**: a raw field the dashboard does not expose (C12 precedent: charge `captured`/`refunded` not on the PI page) is written as **absent**, never guessed; `status` must be a value actually displayed.
- **Never by inference**: no `ESCALATE`, no `RESOLVE`, no `admin_close_case`, no `admin_acquire_claim`/release, no ledger/refund rows, no op completion, no `UPDATE` of any kind; no retries of provider calls; no money or booking action. Observation rows only — **and each INSERT is itself reviewed for its downstream predicate effect (§0.1, §7) before it is made**: the DB does not enforce any of these STOP rules; it enforces shape, status vocabulary, attestation and append-only.
