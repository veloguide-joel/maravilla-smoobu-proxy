# C14 — Contract review: OBSERVING a manual payment / reservation disposition (not executing it) — 2026-11-13
Claude executor · OFFLINE source review, doc-only. Sources: accepted tooling at e7-test `59178b04` (lib, `db/migrations` 0001–0021, `db/lib/admin.js`, `test/db/*`), main `b28619be` (closed; all five flags FALSE). No shared DB / provider / dashboard / run inspection; nothing implemented, no schema / event / runtime change proposed for execution here.

**Policy frame (Joel, 2026-11-13):** refunds are MANUAL and policy-assessed; reservation cancellation ≠ payment disposition; no automated refunds, not even TEST; recording / notification / cleanup HELD. This review is about how the database can *observe* an owner's manual disposition truthfully, with cancellation and payment kept independent — never about performing one.

## 0. Findings in brief
1. **The existing path already suffices for OBSERVATION; no new event or schema is needed to record what the owner did.** `booking.admin_record_evidence` (0003 §C4, superseded in 0010) writes an **owner-attested, dashboard-sourced, append-only `provider_evidence` row** bound to the intent and the provider object (PI / reservation / offline-charge list), with mandatory `attested_by` + `reference`, status vocabulary validation, `observed` JSON (ids / amounts / statuses only), recorded role + session user, admin-only EXECUTE. It changes **no** intent state, version, claim, op, ledger or counter. Accepted tests cover it (`test/db/e2b1-safety.test.mjs` "dashboard evidence: admin only, with attestation and reference"; `e7-test-abort.test.mjs` uses dashboard rows as conflicting evidence).
2. **`ESCALATE` is NOT an observation primitive.** `intent-state.js:321-322, :680-681`: it moves the intent to `reconciliation_required` (new version, `reasonCode`, `alert.owner` effect) and the only exits are `RESOLVE confirmed | released | cancelled` (`:777-792`), each of which *changes state again* and — for a captured payment — cannot be satisfied (`released`/`cancelled` need `authorization_blockers` empty, i.e. PI `canceled`/`requires_payment_method`; a captured PI is `succeeded`). Using it to "note" a manual refund would strand a `payment_captured` intent in `reconciliation_required`. **Do not use ESCALATE for observation.**
3. **`reconciliation_cases` / `reconciliation_resolutions` are not needed for observation either.** Cases are opened only by workers / DB fences (0011/0013/0015/0016 inserts; `mv_booking_app` has no UPDATE, there is no `admin_open_case`); `admin_close_case` requires an open case; `admin_resolve_intent` requires `reconciliation_required`. For a `payment_captured` intent with no open case there is nothing to resolve — and that is correct: a manual disposition does not resolve the booking state, it is a fact *about the providers*.
4. **What the DB cannot express today (gaps, all tolerable for observation):** a manual Stripe refund has **no ledger / `payment_refunds` row** (`payment_refunds` requires `requested_by ∈ {admin, system}` through the guarded request path, `refund_succeeded` is written only by the cleanup repo path, `repo.js:272`); a manual Hostaway cancel of a *captured* booking has no state (`payment_captured` admits no `RESERVATION_CANCELLED`); so after such a disposition **`intents` will keep saying `payment_captured` / `captured_minor` 14000 while `provider_evidence` says refunded / cancelled.** That is an *explicit, queryable discrepancy*, not a silent one, and it is acceptable until a reviewed action exists (§5). It must never be "fixed" by inference.

## 2. Admissible observation record — exact rules (reuse of `admin_record_evidence`; nothing new)
**Actor.** The owner (Joel) attests what he saw / did in the provider dashboards; the row is written by a reviewed admin session (`mv_booking_admin` or the schema owner — ROOT's SQL-editor session qualifies), `attested_by` = owner label, `reference` = where it can be re-checked (dashboard URL + Stripe request id / event id, Hostaway log line time). Claude never writes. The write is **DB persistence** (an INSERT); it is "read-only" only with respect to providers, money and booking state — say so explicitly in any packet.
**Freshness.** `observed_at` = the dashboard read time, ≤ 10 min before the INSERT (packet standard); one row per observation, never back-dated; an observation older than the last state-changing run on that intent is admissible only as *history*, never as the "current" reading.
**Binding (must all hold, checked by the reviewer before the INSERT; the DB checks kind/status/shape only).**
- `intent_id` = the DB intent; `external_ref` = **exactly** `intents.stripe_payment_intent_id` (PI) or `intents.hostaway_reservation_id` (R) — never an id from a different attempt / session; for an offline-charge list, `external_ref` = R and the list is the Hostaway charges page for R.
- Money: `observed.amountMinor` = `intents.final_total_minor`; `observed.currency` = `intents.currency` (USD, upper case); amounts in **minor units** (USD 140.00 = 14000); `amountReceivedMinor`, `amountCapturableMinor`, `amountRefundedMinor`, `chargeId`, `captured`, `refunded` recorded as observed (free JSON keys are allowed by `validate_evidence`; `amountReceivedMinor` is the key the existing resolve predicate reads).
- Identity: for `hostaway_reservation` status `found_active`, `listingId`/`from`/`to`/`totalMinor` must equal the intent's; `bookingRef` = `intents.ref` when visible (field 105433).
- Provenance: `reference` must name the exact artefact (e.g. `stripe:req_…`/`evt_…`, `hostaway:reservation 71700931 logs 2026-11-13 17:56:05Z`).
**Owner-reported vs provider-verified.** A dashboard row (`*_dashboard`, attested) is *owner-reported*; a `*_api` row bound to a succeeded read op is *provider-verified*. Both are admissible observations; only the latter may ever feed an automated predicate, and today only through a reviewed read dispatch (the hosted runners' PI/reservation reads persist evidence in their own flows). Nothing in this review asks for such a dispatch.

## 4. STOP rules for observation (the reviewer applies them; the DB cannot)
- **Stale**: `observed_at` older than 10 min at INSERT, or older than the latest `intent_transitions.at` for that intent → STOP (record only as dated history with `reference` saying so, or not at all).
- **Missing**: any binding field in §2 absent (PI id ≠ intent's, R ≠ intent's, amount/currency missing or in major units) → STOP; `validate_evidence` will also refuse malformed shapes but it does not know the intent's amounts.
- **Conflicting**: an observation that contradicts an existing `*_api` evidence row newer than it, or two owner rows that disagree → STOP; record nothing new until re-read; never pick one by preference.
- **Unknown**: a raw field the dashboard does not expose (C12 precedent: charge `captured`/`refunded` not on the PI page) is written as **absent**, never guessed; `status` must be a value actually displayed.
- **Never by inference**: no `ESCALATE`, no `RESOLVE`, no `admin_close_case`, no `admin_acquire_claim`/release, no ledger/refund rows, no op completion, no `UPDATE` of any kind; no retries of provider calls; no money or booking action. Observation rows only.

## 5. Is anything demonstrably insufficient? Smallest proposal (implementation NOT requested)
Observation itself: **sufficient as is** — reuse `admin_record_evidence`; no migration, no closure impact, no event.
One real insufficiency, scoped and small: **the recording admission does not look at provider evidence**. After a manual refund (D) the intent remains `payment_captured` with `captured_minor` = total, so `intentRefusal` (`offline-charge-proof.js:141-156`) and the 0011 `recording_claim_fence` would still admit a recording of a refunded payment (the fence reads `intents` only). Today this is moot — recording is CLOSED (`executeEnabled=false`, D4 held) — so **no change is needed now**. If recording is ever opened, the smallest guard is a *pure, test-only-first* admission check: refuse recording when the latest `payment_intent` evidence for the intent's PI shows `amountRefundedMinor > 0` or `refunded = true` (a new refusal code, e.g. `PAYMENT_REFUNDED_OBSERVED`, in `intentRefusal` fed by the runner's existing PI read — the hosted capture/recording runners already perform a still-authorized / succeeded PI read). Impact: lib change in the recording closure (new Slice 4 closure digest + pin), one DB predicate optional (`0022`, only if the fence should also read evidence), tests in `offline-charge-proof` + `e7-hosted-recording`. **Proposal only; not for this cycle.**
No change is proposed for cancellation observation, authorization observation, resolutions, cases, claims, refunds or notifications.
