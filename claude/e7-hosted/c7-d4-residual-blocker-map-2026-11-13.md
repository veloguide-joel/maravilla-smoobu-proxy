## 2. Residual blockers — exact conditions (ordered by what the next step would hit first)
### R1 — Recording identity read requires the ref echo and `status = "new"` (code fact, live-proven only for the reservation phase)
- `offline-charge-proof.js:218-225`: the identity snapshot must satisfy `reservationId`, `listingId`, `channelId 2000`, `from`, `to`, `totalMinor`, **`bookingRef === intent.ref` (`IDENTITY_REF_MISMATCH`, :224)** and **`status ∈ ACCEPTED_ACTIVE_STATUSES = ["new"]` (`:34`, `IDENTITY_STATUS_NOT_ACTIVE`, :225)**.
- **No-echo vs recording:** the create reply on 2026-11-13 did *not* echo the ref (`CREATE_REF_NOT_ECHOED:READS_REQUIRED`, `reservation-worker.js:407`, run 43472636610). That is a *create-reply* phenomenon, handled by the reservation worker's READS (by ref + by id, `hostaway-reservations.js:372-380`, `reservation-worker.js:210`). **Live-proven:** the follow-up reads carried the ref (S1-B run 43474198765 → `reservation_confirmed` v7 requires full identity incl. `bookingRef`, `hostaway-reservations.js:334`); C5 UI readback shows field 105433 = `MV-5RBRW6CM` on R71692858. So the ref IS present on `GET /v1/reservations/{id}` after a short delay → **R1 is NOT expected to block recording**, provided the recording's identity read happens after that delay (the runner's fresh read is ≤ 2 min old by rule, not "immediately after create"). *Not yet exercised live by the recording executor itself.*
- **Status "new" only:** any owner touch in the Hostaway UI that changes status (e.g. to `modified`/`confirmed`-like values) would make recording refuse. Any **later** recording admission would therefore require a **fresh status proof** of R at that time (`status = "new"`, identity, ref). This does not constrain the owner's manual, policy-assessed disposition of R71700931 / the captured funds, which remains a separate decision. *Unresolved provider question:* whether Hostaway auto-changes `new` after N days on a Draft listing — UNKNOWN.

### R2 — Every offline-charge provider shape is DOC-DERIVED / LIVE-UNVERIFIED (code fact)

### R4 — No automated exit from a recorded TEST state (policy, not code)
- Code path after `confirmed`: only `TEST_CLEANUP_REQUESTED_RECORDED` (`intent-state.js:152`) → Slice 5 (cancel + Stripe full refund + mirror). **HELD by policy.** Mirror worker additionally needs `MV_E7_TEST_CLEANUP=enabled` + `MV_E7_MIRROR_WORKER=enabled` (`mirror-worker.js:78`) — both absent by design.
- Consequence: a recorded TEST booking stays `confirmed` with a `paid` offline charge in Hostaway and captured TEST funds until the owner disposes manually in Stripe/Hostaway; **no dedicated DB event records a manual disposition** (reservation cancel, Stripe refund, Hostaway refund) performed outside the workers → such a discrepancy between DB and providers **requires explicit, reviewed reconciliation**; the existing `ESCALATE` owner-case / evidence path is available today for that, and a new manual-disposition event (§4.2) is **only a proposal**.

- Meanwhile, by source, `publicStatus` returns "confirmed" from `payment_captured` on (§1 table; source/test fact, not a live observation). Two readings for ROOT to choose between, both compatible with the code: (a) acceptable for TEST (guest page is the only guest-facing surface); (b) for production, "confirmed" without a sent confirmation is a product gap to close under D3, not by changing `publicStatus`.
