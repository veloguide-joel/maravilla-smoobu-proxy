## 2. Finding C21-F1 — documented list example row is refused (reproducer: test D2)
A row shaped exactly like the documented "Get guest charges list" example (an `awaiting` `credit_card_online` charge with **`paymentProvider: null`**) makes `assessChargeList` return `{ ok:false, code:"LIST_ROW_PAYMENTPROVIDER_INVALID" }`, so the WHOLE page is untrusted: the recording worker would stop (no eligibility, no POST) and the merged probe STOPs `LIST_REFUSED/LIST_ROW_PAYMENTPROVIDER_INVALID` (exactly 2 GETs, nothing echoed — asserted). The same row with any documented STRING provider passes and normalises (`amount 10 → 1000 minor`), and the preflight observation counts it as neither marker, look-alike nor same-amount-paid.
- **Safety:** fail-closed — it can only BLOCK recording, never record wrongly. Not a money or Stripe path.
- **Exposure for the bounded TEST flow:** such a row appears only if a non-offline charge (channel autopayment / online payment link) exists on the ONE reservation. C20 observed `rowCount 0` on R71700931 at 23:20Z; the Draft listing has no channel mapping or autopayment rule known to this project. **No current blocker; a latent one for any reservation with provider-less rows.**
- **Smallest fix (PROPOSAL ONLY — not in this PR; would be a reviewed runtime change at a NEW pin):** in `assessChargeList`, accept `paymentProvider` as `string | null` (`typeof === "string" || === null`) while keeping every other `ROW_STRING_FIELDS` string check, the `type` closed list, exact money, and the unchanged `"offline"` equality required by `assessCreateReply` / `assessConfirmingRead` / `expectedObserved` for the ONE marker row. One-line predicate change + one added test case; no DB or schema effect (`0012 recording_list_evidence_ok` validates counts/ids only). Whether to also tolerate `null` in other string fields is UNKNOWN from the docs and should NOT be loosened speculatively.

## 3. Other residuals (no change proposed)
- `count` semantics (§1): documented as a total; accepted equality with page length is a stricter assumption that is correct for ≤ 500 rows at offset 0 and fails closed beyond — acceptable for the bounded flow; a reservation with > 500 charges is not a realistic maraVilla case.
- Probe output enums carry three status values and one provider value the docs do not name (`unpaid`, `pending`, `refunded`; `hostaway`) and lack documented `awaiting`, `pause`, `awaitingHold`, `succeeded`, `braintree`, `authorizeNet` and most documented payment methods. Hygiene-only (labels → `UNKNOWN`, outcome downgraded, never refused). A reviewed constants change could align them to the documented lists; not required for safety.
- `amount` units, create-reply HTTP status and error bodies remain UNKNOWN from public docs; only a live create (HELD) could verify them.
