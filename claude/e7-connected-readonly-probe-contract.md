## 1. Probe-only mode (PROPOSED) — separate from the booking runner
- A separate pure module (§7) runs a fixed, reviewed **probe plan**: an ordered list of probe ids from the allowlist below, each bound to owner-supplied inputs. It never imports the core, workers, journals, DB pools or `run-manifest.mjs`; it does not create, read or repair any journal; it performs no DB access at all.
- Its only provider access is T's `send` over X's `exchange`, so every accepted refusal still applies (fixed origins, path / query / header allowlists, protected ids, `sk_test_`, one exchange per send, no retry, code-only errors).
- **Allowlist = GET only.** No POST / PUT / DELETE: no reservation create / cancel, no PaymentIntent capture / cancel, no offline paid row, no notification / alert, no DB mutation, no journal write or repair. Hostaway `POST /v1/listings/{L}/calendar/priceDetails` is a POST and is **excluded** even though it is computation-only (its shape stays under G-SHAPE).
- **Hostaway token mint is NOT a probe.** `POST /v1/accessTokens` (`client_credentials`, documented; also `lib/hostaway.js:4–6`) is a separate **credential-provisioning gate CP-H** outside the read-only allowlist and is not authorized by any GET approval (§3.2). The existing Stage A client `lib/hostaway.js` must NOT be used: it reads env and re-mints + retries once on 401 / 403 (`lib/hostaway.js:14`, `:164`).

### 1.1 Exact proposed probe inventory (maximum 8 requests per run)
Every probe = exactly ONE T send = one X exchange. Inputs come only from the reviewed plan (§6), never derived from a prior reply.

| Id | Request (wire, via T) | Purpose / gate | Bound inputs | Reply fields needed (checked, then discarded) | Max body | Deadline |
|---|---|---|---|---|---|---|
| P-H1 | `GET /v1/listings/{L}` | G-SHAPE listing; token works for this account's listing | `L` = owner USD test listing | `status`, `result.id === L`, `result.currencyCode === 'USD'` (presence / type only otherwise) | 1 MiB | 15 s |
| P-H2 | `GET /v1/listings/{L}/calendar?endDate=E&startDate=S` | G-SHAPE calendar days | `L`, `S` ≤ `E`, window ≤ 31 days | per-day `date`, `status` / `isAvailable`, `minimumStay` types; day count | 1 MiB | 15 s |
| P-H3 | `GET /v1/reservations?arrivalEndDate=D&arrivalStartDate=D&channelId=2000&includeResources=1&limit=100&listingId=L` (exact H1 query) | G-SHAPE of the lookup the reservation worker uses | `L`, `D` (owner date) | `status`, `result` is an array, per-row key presence / types of `id`, `listingMapId`, `arrivalDate`, `departureDate`, `status`, `customFieldValues` — **count only; no row value retained** | 1 MiB | 15 s |
| P-H4 | `GET /v1/reservations/{R1}` | G-SHAPE reservation read (identity proof fields) | `R1` = owner non-booking sample id, not protected | key presence / types (`id`, `listingMapId`, `channelId`, dates, `totalPrice`, `currency`, `status`, `customFieldValues`) and `result.id == R1` | 1 MiB | 15 s |
| P-H5 | `GET /v1/guestPayments/charges?limit=500&reservationIds={R1}` | G-AUTH (Bearer on this READ endpoint), G-FILTER, G-SHAPE list | `R1` | `status`, row count, per-row `reservationId` equality with `R1` (boolean only), key presence / types of `id`, `type`, `title`, `amount`, `currency`, `paymentMethod`, `status` | 1 MiB | 15 s |
| P-H6 | `GET /v1/guestPayments/charges?limit=500&reservationIds={R2}` (control) | G-FILTER control | `R2` ≠ `R1`, not protected, owner states both have ≥ 1 charge | as P-H5 + disjointness of charge-id sets (boolean) | 1 MiB | 15 s |
| P-S1 | `GET /v1/account` | credential's account = expected id | `acct_…` (owner) | `object === 'account'`, `id === acct` (T check) | 256 KiB | 15 s |
| P-S2 | `GET /v1/payment_intents/{pi}?expand[]=latest_charge` | B4 read shape under the selected `Stripe-Version`; TEST mode of a PaymentIntent | `pi` = owner existing TEST PaymentIntent (no new one is created) | `object`, `id`, `livemode === false`, and presence / types of the proof fields `capture-proof.js:54–66` reads (`status`, `capture_method`, `amount`, `amount_capturable`, `amount_received`, `currency`, `metadata`, `latest_charge.{object,id,payment_intent,status,paid,captured,amount,amount_captured,amount_refunded,currency,livemode,payment_method_details.card.capture_before}`) | 256 KiB | 15 s |

- **Run bounds:** ≤ 8 requests, strictly sequential, total deadline 3 minutes; each probe gets its own `AbortSignal` (`AbortSignal.timeout(15_000)` composed with the run signal by the future CLI — X itself owns no timer). P-H6 runs only if the plan includes a G-FILTER control; P-S2 only if the owner supplies a TEST PaymentIntent.
- **Output codes (fixed):** `PROBE_OK`, `PROBE_SHAPE_MISMATCH`, `PROBE_HTTP_<status class>`, `PROBE_AUTH_REFUSED` (401 / 403), `PROBE_REDIRECT_REFUSED`, `PROBE_TRANSPORT_FAILED`, `PROBE_ABORTED`, `PROBE_TIMEOUT`, `PROBE_PROTECTED_SEEN`, `PROBE_FOREIGN_ROW`, `PROBE_ACCOUNT_MISMATCH`, `PROBE_LIVEMODE_REFUSED`, `PROBE_PLAN_INVALID`, `PROBE_NOT_RUN`.
- **Stop rules:** the run STOPS at the first probe whose code is not `PROBE_OK`; later probes are `PROBE_NOT_RUN`. **Zero retry, zero fallback** (no alternate header, scheme, host, query, page or id). Any timeout / abort / transport failure / ambiguous output is a STOP even though a GET has no intended effect. One request per probe, never re-sent.
- **Protected ids:** the plan validator refuses any protected id as `L`, `R1`, `R2` or any value (T and X also refuse). If a protected id appears **in a reply** (e.g. a P-H3 row), the probe returns `PROBE_PROTECTED_SEEN` and STOPS; nothing about that row is kept. No unfiltered or global charge list is ever requested; P-H5 / P-H6 always carry exactly one owner id.

## 2. What the probes can and cannot establish
| Gate | Read-only evidence that would CLOSE it (scope only) | What read-only data CANNOT establish |
|---|---|---|
| **G-AUTH** | P-H5 / P-H6 `200` with `Authorization: Bearer` → Bearer accepted on the guest-charges READ endpoint for this token | That `POST /v1/guestPayments/charges/{R}` (H9) accepts Bearer (its doc examples show `jwt`). A 401 / 403 → `PROBE_AUTH_REFUSED`, STOP — **no automatic switch to a `jwt` header, no re-mint, no retry**; any alternative auth form needs its own reviewed change. H9 auth stays OPEN until a write is separately approved. |
| **G-FILTER** | P-H5 rows all with `reservationId == R1` AND P-H6 rows all `== R2` AND both non-empty AND disjoint charge-id sets | **An empty list proves nothing** about filter correctness (P-H5 empty → G-FILTER stays OPEN). One reservation with charges cannot prove other reservations were excluded; hence the owner-approved control `R2`, bounded to 1 extra call. A non-matching row → `PROBE_FOREIGN_ROW`, STOP; nothing from that row is kept. |
| **G-SHAPE** | Presence / types of the listed reply fields for P-H1–P-H6 | Write shapes: create (H6), cancel (H7), offline charge (H9) and priceDetails (H5) replies are **not** inferred from read shapes. G-SHAPE closes only for the read routes probed. |
| **B4** Stripe-Version | P-S2 with the explicitly selected version: proof fields present with expected types, `livemode:false` | Capture / cancel reply shapes under that version; account-default behaviour; anything about live mode. |
| **TEST mode** | P-S2 `livemode:false` on a PaymentIntent and its latest charge; T's `sk_test_` prefix rule | **P-S1 cannot prove TEST mode** — the Account object has no `livemode` (transport contract §3.2). P-S1 proves only that the credential's account id equals the expected id. |
| Account ownership | — | Neither provider read proves who owns an account. The Hostaway account label and Stripe account id stay TRUST inputs (adapters `:403`). |

## 3. Credentials (PROPOSED design; no secret read or requested now)
### 3.1 Ingress, lifetime, redaction
- **Never** requested, pasted or printed in Claude / ChatGPT chats, browser messages, the plan / manifest, argv, JSONL, reports, git, test fixtures or environment dumps. Claude never sees a value.
- **Ingress:** one owner-created local file OUTSIDE the repository, chosen by path in the plan (the path is not secret). The future CLI preflight refuses unless: regular file (not a symlink), owned by the invoking user, mode exactly `0600`, size ≤ 4 KiB, not under the repo / any git work tree, exact JSON keys `{ hostawayToken, stripeTestKey }` (either may be absent when the plan has no probe for that provider). Values are read once, validated by shape (`hostawayToken` printable ≤ 4096; `stripeTestKey` `^sk_test_[A-Za-z0-9]+$` — T refuses everything else again), and handed to T only as the injected `credential()` closures. **Rejected alternatives:** argv (visible to other local users), env vars (inherited by children, appear in crash / env dumps), stdin piping from shell history.
- **Lifetime:** values live only in the probe process's memory for the run; nothing writes them anywhere. On exit the process ends; the owner deletes or rotates the file per the package. **No claim of memory erasure** — JavaScript strings cannot be provably wiped; the guarantee is "never persisted or emitted by this code", not "erased".
- **Redaction:** T places a credential only in the private exchange request's `Authorization` header; X never reads it beyond the header shape; the result schema (§5) has no field that could hold it; errors are code-only.
### 3.2 Provision vs access
- **Credential provision** = making an EXISTING TEST credential available locally to this run. **Granting new access** (creating keys, OAuth apps, users, scopes, Hostaway API client ids, Stripe restricted keys) is out of scope and not part of any probe approval.
- **CP-H (Hostaway token):** the probe consumes a pre-existing access token. Minting it needs `POST /v1/accessTokens` — a credential-provisioning step outside the GET allowlist. Proposed: the owner mints it with his own tooling, or a separately reviewed mint slice; either way it is its own line in the approval package, never implied by GET approval. Token expiry / revocation is not handled by the probe (a 401 / 403 is a STOP).
- **Stripe:** `sk_test_` secret key only (restricted keys refused, T `:346`); the exact expected `acct_…` id is a plan input (T binds it at construction).
### 3.3 Stripe-Version (B4) — explicit selection, no synthetic promotion
- The synthetic test pin `2099-01-01.synthetic` is never promoted. The real value must be an explicit plan input matching T's format (`:345`) and a version documented by Stripe.
- Primary-source facts (read 2026-11-04): Stripe's versioning page names **`2026-10-28.endive`** the current version; Endive's first version **`2026-09-30.endive`** is breaking and, among others, **removes `payment_method_types` from Checkout Sessions** and from Payment Intents / Setup Intents. The last Dahlia GA version is **`2026-08-26.dahlia`** (in Dahlia, the Payment Intents `payment_method_types` removal is in the August **preview** channel only).
- Repository fact: the accepted TEST checkout builder sends `payment_method_types: ["card"]` (`lib/checkout/stripe-test-mode.js:97`), and `lib/stripe-checkout-draft.js:98` pins `2022-11-15`.
- **Recommendation (open decision for root / owner):** select ONE version for the whole later connected flow, not only the probe. `2026-08-26.dahlia` is the conservative candidate compatible with the accepted checkout parameters; `2026-10-28.endive` would require a separate review of the checkout builder first. P-S2 then checks the proof fields under the selected value; B4 closes only for those read fields.

## 4. Owner environment preflight + native validation (PROPOSED)
- **Fail-closed preflight in the future CLI only** (modules stay env-free): `process.versions.node` within an explicitly reviewed supported set — proposed `22.22.x` (Claude-inspected source) and `24.22.x` (root-inspected); anything else → `PROBE_ENV_UNSUPPORTED`. Refuse if `NODE_TLS_REJECT_UNAUTHORIZED` is set at all, `NODE_EXTRA_CA_CERTS` is set, or `process.execArgv` / `NODE_OPTIONS` contain `--use-env-proxy`, `--use-openssl-ca`, `--use-system-ca`, `--insecure-http-parser`, `--tls-*`, `--require` / `--import` / `--loader`; `NODE_USE_ENV_PROXY` set. X already pins `rejectUnauthorized:true` and uses a proxy-free dedicated Agent, but the preflight records and refuses the environment rather than relying on that alone.
- **Default primitive vs fake:** the probe CLI uses X's default `node:https` primitive; probe-module tests use only fakes. The CLI prints which primitive it uses (`default-node-https`) as a code, nothing else.
- **Not established by fake tests:** native v22 / v24 event ordering, real TLS verification, DNS, socket behaviour, Agent teardown on a real socket. A separately scoped **loopback / native validation** (NOT run, NOT automatic, needs its own authorization) could resolve: actual `ClientRequest` / `IncomingMessage` event order on the owner's Node, `rawHeaders` / `complete` semantics, abort / destroy teardown, no socket leak. It would need a local TLS endpoint, which X deliberately cannot trust without a CA option — so it needs either a test-only primitive or a plain local server with a reviewed exception; that is a design question for root, not part of this slice.

## 5. Probe result format (PROPOSED)
- **Run summary (code-only, safe to show anywhere):** `{ schema:'e7-probe-result-v1', planHash, reviewedCommit, nodeVersion, stripeVersion, startedAt, endedAt, outcome:'COMPLETED'|'STOPPED', stopCode, probes:[{ id, code, httpStatus|null, elapsedMsBucket }] }`. No URL, path, id, query, header, credential, body or provider text.
- **Durable evidence (allowlist only):** per probe a fixed set of booleans / small enums / counts, e.g. P-H5 `{ rowCount, allRowsMatchR1:true, keysPresent:{…:true} }`, P-S2 `{ livemode:false, latestChargeLivemode:false, proofFieldsPresent:{…}, status:'requires_capture'|… }`, bound to `{ planHash, reviewedCommit, stripeVersion, nodeVersion, probedAt }`. **No hashes of low-entropy PII** (names, emails, dates, amounts) — hashing them is not anonymisation and is not done. Reservation / listing / PaymentIntent ids appear only as plan references (`R1`, `R2`, `L`, `pi`), never echoed from replies.
- **Bodies:** successful reply bytes exist only transiently inside T's decode; the probe extracts the allowlisted booleans / counts and drops the parsed object. Guest, payment and provider bodies are never logged, printed, written or journaled.
- **Uncertainty:** a timeout / abort / transport failure / unparsable reply is `STOPPED` with that code; it never claims "no effect" and is never retried. **Passing probes do not authorize any booking run** or any write.
