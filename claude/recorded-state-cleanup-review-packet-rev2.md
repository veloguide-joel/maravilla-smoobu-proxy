## 7. Race-safe pristine-notification suppression (F5)
- Transaction = the E4 request's `applyEvent` tx, accepted lock order: `intents FOR UPDATE` → `intent_work FOR SHARE` → `payment_attempts FOR SHARE` → `external_operations FOR SHARE` (all rows) → then the notify row `FOR UPDATE` (escalating the share lock on that one row) → fence checks → `INSERT booking.notification_write_authority (txid, operation_id, action 'suppress')` → `UPDATE … SET state = 'superseded'` → `INSERT booking.notification_suppressions (op id, intent id, intent version seen, reason 'TEST_CLEANUP_RECORDED', by, at)` (append-only; UPDATE/DELETE/TRUNCATE triggers as `notification_renders`).
- Fence (0021, trigger on the `pending → superseded` UPDATE): authority row for this txid+op+`suppress` present (least privilege: the function is SECURITY DEFINER, the app role has no direct UPDATE path to `superseded`); `OLD.attempts = 0 AND OLD.dispatched_at IS NULL AND lease_worker_id IS NULL AND lease_until IS NULL AND late_result_status IS NULL`; NO row in `notification_renders` for the op; NO row in `notification_latches` for the op (a latched row is owner-visible — suppression refused `NOTIFY_LATCHED`); the intent row is locked by this tx in state `confirmed` moving to `test_cleanup_pending`; `NEW.attempts = OLD.attempts`, no lease, no result, no completion. Anything else → `NOTIFY_SUPPRESS_FENCED`; the whole request rolls back (no partial state).
- Race with the dispatcher's `claim_guest_notification` (CORRECTED, full called graph): the claim's lock order is `gn_lock_bundle` = `intents FOR SHARE` → `hostaway_reservation_attempts FOR SHARE`, then `intent_work FOR SHARE`, then the op `FOR UPDATE` (**[SOURCE]** 0016 :617–639, :730–732). The request's order (accepted `applyEvent`) is `intents FOR UPDATE` → `intent_work FOR SHARE` → `payment_attempts FOR SHARE` → `external_operations FOR SHARE` → `hostaway_reservation_attempts FOR SHARE` (repo.js :49, :495–:511) → the notify row `FOR UPDATE`. Both writers take the SAME first lock — the intent row — and SHARE conflicts with UPDATE, so they serialize at the intent row: whichever holds it first runs to commit while the other waits; neither holds any later lock the other needs while waiting at the first → no cycle. Exactly one winner: (a) claim first → row `in_flight`/attempts 1 → the request's fence sees `attempts <> 0` → the request REFUSES read-only (`TEST_CLEANUP_NOTIFY_CLAIMED`), nothing written, intent stays `confirmed`, the notification proceeds under 0016 (we never cancel an attempted send); (b) request first → row `superseded` → the later claim reads `state <> 'pending'` → `NOT_PENDING` (**[SOURCE]** :739). `superseded` is excluded from dispatch selection (**[SOURCE]** 0016 selects `state = 'pending'`, :658), from recovery (`in_flight` only, :893) and from any reset ("no reset" rule, :580 kept); 0021 adds `superseded` to the terminal set so no transition leaves it.
- Tests (DB negative): claim-then-suppress refuses; suppress-then-claim `NOT_PENDING`; suppress with attempts 1 / dispatched / leased / rendered / latched refused; suppress without authority row refused; direct UPDATE by the app role refused; audit row mandatory (suppress without insert → refused by a deferred constraint trigger); audit rows append-only.
